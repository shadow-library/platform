# Synapse

The platform's AI service. Every model call from every app goes through it: apps name a task, Synapse picks the model, translates for the provider, applies effort, enforces budgets and records usage.
`synapse-server` is the API and dispatch engine; `synapse-web` is an admin console over it (presentation only, no business logic). `packages/synapse` is the client (typed calls and a LangChain chat model).
Authentication is Identity's job (`docs/identity.md`).

## Concepts

- Provider: an upstream endpoint with a kind (`openai`-compatible, `ollama`, `mock`), a locality (`in_cluster`, `host`, `third_party`), a cost class (`zero` or `metered`) and features (`sessions`, `native_web_search`, `image_input`). Its API key is a stored credential it names by id (`credential`), never a value in the catalog. The older `apiKeyConfig` (a Config key name) is deprecated, kept one release, and cannot be combined with `credential`; its only key, `synapse.provider.openrouter.api-key`, is bound to `https://openrouter.ai` like a credential, at publish and at call time. An `ollama` provider sends no key.
- Credential: a provider API key an admin creates, rotates and revokes in synapse-web, sealed in Synapse's database with the `@shadow-library/common/crypto` envelope under the `synapse.crypto.keys` keyring. It is bound to one origin (scheme, host, non-default port), and a provider whose URL has another origin can neither publish nor call with it. The secret is write-only: responses carry a hint of at most a quarter of it (the first six and last four characters from 40 characters up, the last four from 16, else nothing) and the keyring key that wraps it. Revoking is permanent and refused while the published catalog names the credential.
- Model: a catalog entry with capabilities (tools, structured output native or by prompt, vision, image output, embedding dimensions, context, reasoning mode and supported efforts, prompt cache, sampling), list prices per million tokens, and ordered deployments (provider plus the provider's own model id). Deployment order is failover order.
- Alias: the user-facing family name ("Opus", "GPT Sol") that targets one model. The admin chooses the target, so moving "Opus" to a newer model changes what users get without any app change. The version is hidden by default and shown only when the alias opts in. States: `active` (offered and usable), `hidden` (usable by key but not offered), `retired` (never offered; a request naming it falls through to the task's routes).
- Task: the app's contract, keyed `<app>.<name>` and callable only by that app. Declares kind (chat, embedding, image), required capabilities, an effort range (default, min, max), a data policy (`any` or `in_cluster_only`), the aliases it accepts, and its routes, with an optional display `label` and `description` for the admin console that are never exposed to apps. An embedding task is pinned: its route models cannot change across catalog versions, because stored vectors depend on them.
- Route: a model chosen by selectors the caller sends (`tier`, `content_mode`, `plan`, ...). The route with the most matching selector keys wins, ties go to the earliest; exactly one route has no selectors and is the default.
- Budget: a limit on calls and/or list-price cost for an app, per subject or for the whole app, over a fixed window (`1h`, `1d`, `30d`). Cost is counted at list price, never at what a provider billed.
- Catalog: one JSON document holding providers, models, aliases, tasks and budgets. Versions are `PUBLISHED` (the active one is the highest) or `ARCHIVED`; there is no draft, and `DRAFT` rows the removed draft workflow left in a database are never read. Every confirmed change goes live on its own: it replaces the whole document atomically after validation as the next version, against the active version it was made on (none, for the first catalog), and is refused with a conflict when another version went live since; a document equal to the active one publishes nothing and answers the active version. A budget-only publish replaces only `budgets` of the active version the same way. Rollback copies an older document into a NEW published version against the expected active version, so history is append-only and an undo never reverts a newer change. Replicas poll the published version and keep the previous one if a reload fails.
- A baseline seed writes catalog v1 only when no version exists. The `local-only` seed profile replaces every deployment with local Ollama, so the test environment makes no paid call.

## Architecture

- Callers are Identity M2M clients (`novel-forge`, `memoir`); the calling app is the token's client id, and a task whose prefix is not the caller is refused. Each caller needs a service-access rule in Identity for `api://synapse`.
- Request contract on `/api/v1/*` (OpenAI-compatible chat, embeddings and image generation): the body is the OpenAI body with `model` set to the task id, plus a `synapse` envelope carrying the caller-generated `request_id` (unique), the `subject` (owner, user or app), `selectors`, and optionally an `alias`, an `effort`, a `session` and `web_search`. The only header is `Authorization`. A request without the envelope is invalid.
- The response is the OpenAI shape, with `model` echoing the task id, plus a `synapse` block: `alias` (the alias key, or null), `label` (the alias label, plus the model version when the alias sets `showVersion`, else the model label), model, provider, effort applied, attempts, catalog version and list and billed cost (`cost.list_usd`, `cost.billed_usd`). Streams end with one choice-less frame carrying usage and that block, then `[DONE]`.
- `GET /api/v1/catalog` tells an app what a user may choose for a task and selectors: the default, the active matching aliases with their target model, price and capabilities, and, for the default and for each alias, whether its model's first eligible provider has native web search. Without `task` it returns every task of the calling app. It is ETag-cached by catalog version, so apps render pickers from it and hold no model list.
- Resolution: task, then the alias if the caller names one and the task accepts it and its `available` rule matches the selectors, otherwise the routes; deployments are then filtered by the data policy and the request's needs. An empty result is refused, never silently relaxed.
- Dispatch: budgets are admitted first, then effort is clamped to the task's range and snapped to what the model supports, then deployments are tried in order. A duplicate `request_id` is refused with `SYN_DUPLICATE_REQUEST` before dispatch. Settlement after the response writes the usage ledger row and adds list cost to every admitted budget.
- Provider translation is Synapse's job alone: model id substitution, effort encoding per provider kind, session and web-search switches for the host gateway, structured output native or injected into the prompt, cache-control kept or stripped, sampling parameters dropped for models that reject them, Ollama's OpenAI-compatible endpoints, image generation endpoints, and usage parsing including cached and reasoning tokens. Apps never see a provider dialect.
- Own PostgreSQL database: `catalog_versions`, the `ledger`, `budget_counters`, `provider_credentials` and their audit trail `credential_events` (one row per create, rotate and revoke). A daily retention sweep prunes the ledger.
- Credentials at call time: a secret is decrypted on first use and kept in the replica's memory under its id and version. Each replica polls every credential's version and revocation at the catalog poll interval, so a rotation or revocation reaches it within one interval, and the replica that made the change drops its copy at once. A revoked credential, a provider outside the credential's origin, or a secret that cannot be decrypted fails the call without failover. Provider calls never follow a redirect, which would carry the key past its origin; a 3xx fails the call. Publish and rollback check every named credential exists, is live and matches the provider origin, under the catalog lock a revocation also takes.
- Keyring: `synapse.crypto.keys` lists `kid:key` entries; the first seals, every one opens, and a malformed value fails boot. A replica whose keyring lacks a key some stored credential uses fails boot (retrying only while the database is unreachable), so expect CrashLoopBackOff until the key is restored. Once ready, one replica at a time (advisory lock) re-wraps rows onto the active key, each write a compare-and-set on the row's version and kid, and logs the outcome; `GET /api/v1/admin/credentials/status/keyring` shows how many rows each key still wraps, and a key leaves the keyring only at zero.
- The migrate hook imports `synapse.provider.openrouter.api-key`, kept one release as an import source only: when it is set and no credential named `openrouter` exists, it becomes one bound to `https://openrouter.ai`, and the providers naming that env key at that origin move onto it in a new catalog version, once. After the import, rotate the key in synapse-web, not in the environment.
- `synapse-web` is a console over the catalog for finance, product and engineering: spend overview, usage, budgets, features (tasks), model names (aliases), models, history with undo and restore, providers, credentials, and an advanced JSON editor. Its structured forms change only the fields they edited on the active version, apply after a confirm step that says what changes and for whom, and refuse a concurrent change to the same field, except one that already holds the value they set, which reads as already live (a retry after a lost response); validation stays server-side.
- Editors are stored by subject id only (`created_by`, the user token's `sub`). Admin responses that carry `createdBy` (catalog versions, credentials) add `createdByName`, the display name Identity's user directory gives at read time, batched per response and cached per replica for minutes; it is null for `seed`, `import` and anyone Identity will not name, and when Identity fails or does not answer within a couple of seconds the response still succeeds with the last known name or null.
- Budget status reports the active catalog's budgets over their current fixed UTC windows, read from the counters (list price). The usage series is gap-filled daily per group.
- `synapse-web` calls same-origin `/api/*` in the browser and `synapse-server` directly during SSR, and authenticates via Identity; its `api-types.gen.ts` is generated from `synapse-server`. It hides the controls a user lacks the permission for, read from `GET /api/v1/admin/access`; the server enforces every permission regardless.

## Integrations

- `identity`: Synapse is an `INTERNAL` app. Service scopes `synapse:infer` (inference) and `synapse:catalog:read` (catalog); these are distinct from the user permissions, and inference and catalog routes admit only service principals while `/api/v1/admin/*` admits only users. Service-access rules name exact paths, never a wildcard covering the admin routes. The `synapse` client holds Identity's `users:resolve` to name editors; Identity names only users holding a consent with that client, which signing in to the console records. User permissions `synapse:catalog:read`, `synapse:catalog:write` (changing the live catalog), `synapse:providers:write`, `synapse:budgets:write`, `synapse:usage:read` and `synapse:credentials:manage`, grouped into roles `SynapseViewer`, `SynapseOperator` (adds `synapse:catalog:write`), `SynapseFinance` (viewer plus `synapse:budgets:write`), `SynapseAdmin` (adds `synapse:providers:write` and `synapse:budgets:write`; granted to the bootstrap admin) and `SynapseCredentialsAdmin` (`synapse:credentials:manage` alone, checked with the short high-risk decision cache; granted to the bootstrap admin). Whoever holds both provider editing and credential management can bind a key to any origin, so only owners should hold both. Holders of `synapse:budgets:write` publish budgets without `synapse:catalog:write`; that publish checks the permission with the short high-risk decision cache. A change or rollback that changes `budgets` also needs `synapse:budgets:write`, and one that changes `providers` needs `synapse:providers:write`, in addition to `synapse:catalog:write`; both are checked with the short high-risk decision cache. The permission catalog MUST match Identity's seed: edit both together.
- `novel-forge`: tasks `novel-forge.{writing,planning,review,chat,helper,vision,image,embedding}`, selectors `tier` and `content_mode`; chat pins store alias keys; spend limits are Synapse budgets per owner.
- `memoir`: tasks `memoir.insight` and `memoir.receipt-structuring`, selector `plan` (`free` or `paid`). memoir's entitlement quotas stay in memoir.
- The host CLI gateway is the `subscription` provider: zero cost, sessions and native web search, a small per-replica in-flight cap. OpenRouter is the metered third-party provider; local Ollama serves embeddings and memoir's default routes (`llama3.1`), and replaces every deployment in the `local-only` profile.

## Hard rules

- NEVER store prompt or completion text: the ledger holds identifiers, tokens, cost, timing and outcome only, and logs carry no message content.
- NEVER rename or delete a task id: apps depend on it. NEVER rename or delete an alias key: stored pins depend on it, so retire it instead. Publish rejects a document that drops either.
- NEVER edit a published version or write catalog rows outside the change, budget publish and rollback code. Every publish MUST validate the whole document, with errors carrying a JSON path; a dangling reference, a route lacking a required capability, an unordered or unsupported effort range, an `in_cluster_only` task that can reach a non-in-cluster provider, a pinned task whose models changed, or a task without exactly one default route is refused.
- Failover happens only before the first byte reaches the caller, and only on a connect error, 408, 429, 5xx, a 400 with `unsupported_parameter`, or a deployment at its in-flight cap. After that an error is an error frame, never a retry on another deployment. When every deployment fails the call is `SYN_PROVIDERS_EXHAUSTED`.
- Client disconnect and timeout MUST abort the upstream request on every path; the ledger records `cancelled`.
- Providers own their capacity: Synapse neither queues nor throttles beyond a deployment's in-flight cap.
- Any replica serves any request. Shared state lives only in Postgres and changes by atomic statements: budget admission is one conditional upsert per budget, `request_id` uniqueness is claimed before dispatch, and the retention sweep and the credential rewrap run under advisory locks. Per-replica memory holds only the catalog cache, decrypted credentials keyed by version, in-flight counts and a bounded, minutes-long cache of editor display names.
- A budget counts list price, so a free subscription call still spends budget.
- The `data_policy` of a task is enforced at resolution; no seeded task uses `in_cluster_only`.
- No app other than Synapse may hold a provider key, URL or vendor model slug, and apps MUST NOT read Synapse's database.
- NEVER log, return or store a credential's plaintext; logs name a credential by id. A sealed secret's context is `synapse:provider_credentials:<id>:secret`, from an id generated before insert, and a rotation seals under the same context.
- NEVER remove a keyring key while `status/keyring` still counts rows on it.
- Every route needs an auth decorator; inference routes need the service scope and the admin routes a user permission, except `GET /api/v1/admin/access`, which needs only a user session and reports which Synapse permissions the user holds. Bots are refused.
- A server contract change requires regenerating `synapse-web`'s `api-types.gen.ts` and fixing its callers.

## Known limits

- Origin binding is an application control, not a cryptographic one: `allowed_origin` is a plain column outside the envelope, so someone with write access to the database can rebind a credential, and can restore an older envelope of the same credential, which the row's context still opens.

## Non-goals

- No prompt storage, prompt templates or caching of completions. No per-provider rate limiting. No billing: budgets are guardrails, not invoices.
