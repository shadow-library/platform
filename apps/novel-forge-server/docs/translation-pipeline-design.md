# Translation Pipeline Design

A translation pipeline for original-language novels: it turns a project's original-language chapters into natural English prose, backed by a per-project
terminology glossary with a suggestion review queue, per-chapter fidelity checks, and a finalize step that commits reviewed English into canon — consistent
across thousands of chapters and whatever originals arrive later. This doc drives tasks TL0–TL9 in CLAUDE.md and follows the conventions of
`ai-system-design.md` (its Appendix A hard rules apply unchanged).

**Supply model.** There is no bundle import. The user creates a project in the app and declares its original language. Original chapters arrive two ways, both landing through one service method: the user pastes a chapter in the translation screen, or an external app pushes chapters through an API-key-authenticated endpoint. The curated-ingest surface (`src/modules/curated-ingest/`) is the precedent for the push door: row-locked append, contiguity rule, digest manifest, ownership proven against the key owner.

This plan mirrors the rebrand pipeline (`docs/rebrand-pipeline-design.md`, `src/modules/rebrand/`, `src/modules/ai/graphs/chapter-rebrand.graph.ts`, `JobExecutor.runRebrand`) wherever the shape fits and calls out every deliberate divergence. Paths are relative to `apps/novel-forge-server` unless marked web.

Nothing in the codebase knows about languages today: `projects` has no language column, `chapters.content` is assumed to be English by every consumer (publishing, rebrand, reforge, extraction, retrieval, recombine), and the residue scan treats CJK characters as a defect. Translation therefore sits _upstream_ of every existing pipeline.

## 1. Design decisions

### D1. Original prose gets its own columns; `chapters.content` remains "the English prose every pipeline reads"

- Add `chapters.original_title`, `chapters.original_content` and `projects.original_language` (ISO-639-1 / BCP-47 string, e.g. `zh`, `ko`, `ja`; `null` = English, translation not applicable).
- A pasted or pushed original creates the `chapters` row with the **original** columns filled and `title`, `content`, `word_count` `NULL`, `status = 'done'`, `generator = 'human'`, `locked = false`. `content_hash` is stamped with the digest of the original `{title, content}` (same `chapterContentHash` helper curated ingest uses), so the push manifest is a projection, never a re-hash.
- **Finalizing** a translation copies the reviewed title/body into `chapters.title` / `content` / `word_count`, sets `locked = true`, in the same transaction that flips the translation status. A finalized translation is then indistinguishable from a curated-ingest `final` chapter: human provenance, locked, publishable.

Why: `publish-payload.ts:30-41` reads only `chapters.content` and gates on `locked` (`publishing.service.ts:185-189`, `PUB_002`); `publish-runner.ts:383-388` refuses to push on hash drift; rebrand/reforge `loadChapter`, extraction, indexing, catalog and recombine read the same column. With D1 every downstream consumer keeps working unchanged and only ever sees _finalized_ English; untranslated chapters are excluded for free because `content` is already nullable (`chapters.ts:30`). The original is written only by the originals door, never by the pipeline, so "translation failure cannot corrupt the original" is structural.

Rejected: side table plus a resolver in every reader (six or more read paths and the publish hash guard). Rejected: overwriting the original in place.

**Project kind.** See D10: `project_kind` becomes the workflow axis with four values, and translation is gated on `kind = 'translation'`. A finalized translated chapter has the same shape curated ingest already produces (human provenance, locked, publishable), so publishing needs nothing new. Rebrand and reforge stay `source`-only and untouched.

### D2. Translation drafts live in `chapter_translations`, one row per `(project_id, chapter)`

Same side-by-side shape as `chapter_conversions` (`schemas/rebrand.ts`). Status enum `chapter_translation_status`: `translated | attention | finalized | failed`. "Untranslated" is the absence of a row and is derived, never stored. Columns beyond the rebrand precedent:

- `applied_terms jsonb` — `{ [glossaryEntryId]: revision }` for every glossary entry rendered into the chapter's slice, GIN indexed. This lets a glossary edit propagate in one indexed statement instead of a body scan over thousands of rows.
- `glossary_stale boolean` — set when any applied entry changed after the translation was produced.
- `source_hash varchar(64)` and `source_stale boolean` — the original's digest at translation time; the originals door flips `source_stale` when it overwrites an original that already has a translation.
- `segments jsonb` — `[{ sourceStart, sourceEnd, body }]` alignment metadata kept for the audit; the joined `body` remains the truth. Its `issues` entries (shared with `chapter_conversions`) persist a 0-based `segmentIndex` into this array; the audit prompt and its schema report a 1-based index keyed to the numbered segment headings shown to the model, and an out-of-range answer degrades to a whole-chapter issue rather than a bad index.
- `last_error varchar(2000)`, `last_failed_run_id uuid`, `edited_at`, `finalized_at`.

### D3. One glossary table with a lifecycle — not a suggestions table plus a glossary table

`translation_glossary`: `source_term` (unique per project), `variants jsonb`, `target`, `category` (`character | place | organization | profession | title | rank | ability | item | creature | term`), `treatment` (`translate | localize | transliterate | preserve`), `meaning text`, `context_excerpt text`, `alternatives jsonb` (`[{ target, rationale }]`), `status` (`suggested | approved | rejected`), `origin` (`seed | discovered | manual`), `created_chapter`, `revision`, `decided_at`.

Divergences from `rebrand_glossary`, which is monotonic by design:

- **Edits are allowed.** `PATCH` bumps `revision`, and one statement marks dependents: `UPDATE chapter_translations SET glossary_stale = true WHERE project_id = $1 AND applied_terms ? $entryId` (finalized rows included — they keep their status but show the stale badge).
- **`suggested` entries are provisional-binding.** Rendered to the model as "provisional — use unless told otherwise", so the same term renders identically across chapters before anyone reviews it. Approval with a modified target makes earlier chapters stale by the same mechanism.
- **`rejected` means "not a term".** Rendered as a short "translate these normally" line and filtered deterministically from `discoveredTerms` in `mergeGlossary`, so the model cannot re-suggest it every chapter.
- **Treatment distinguishes translate/localize from transliterate/preserve**, which the spec requires. `preserve` entries also allowlist the source-script residue check (D6).

### D4. Finalize is the only gate that writes canon, and it is strict

`POST /translation/chapters/:n/finalize` requires: status `translated` or `attention`; zero `suggested` entries among `applied_terms`; `glossary_stale = false`; `source_stale = false`. It then, in one transaction, writes `chapters.title/content/word_count`, sets `locked = true`, and sets status `finalized` with `finalized_at`. `reopen` flips status back to `translated` without clearing `chapters.content` — the last finalized text stays canonical (and published) until the next finalize replaces it. A re-finalize of an already-published chapter runs the same hash-move decision the amend path uses (`decideAmendRepublish` in `src/common/amend-republish.ts`) and schedules a republish only when the digest moved.

### D5. Job kind `translate`, three data-derived phases, flag-and-continue, never clobber

Phases mirror `runRebrand` (`job.executor.ts:204-256`): verify originals exist → seed (idempotent on `translations.style_notes`) → translate ascending, with progress `{done,total,current,phase}`. Three deliberate divergences:

1. **`settings.pauseAfterSeed` (default `true`).** When the seed produced suggestions, the job finishes after phase 2 with phase `review`. The seed is the one moment where review is cheap and high-leverage: protagonist and faction names will appear in every one of thousands of chapters. A second `POST` continues into phase 3 (seed is a no-op then). Setting it `false` gives rebrand's zero-touch behaviour with provisional terms.
2. **`recordFailedTranslation` never overwrites a good row.** If a non-failed row exists it only stamps `last_error`/`last_failed_run_id`; only when no row exists does it insert `status = 'failed'` with an empty body. (`recordFailedConversion` at `job.executor.ts:507-528` flips status to `failed` while keeping the body; here the status must stay truthful because it gates finalize.)
3. **Finalized rows are never targets**, even under `force`. Re-translating a finalized chapter requires `reopen` first (`TRN_004`).

Target selection (`selectTranslationChapters`): `payload.chapters` wins (deduped, sorted) and is exempt from the done-skip regardless of `force`; else `payload.stale = true` selects rows with `glossary_stale` or `source_stale`, also exempt from the done-skip; else every chapter with `original_content`. `finalized` rows are dropped from every path unconditionally; `translated`/`attention` rows are dropped only from this last, data-derived path, and only when `force` is unset. `limit` caps the resulting list for trial runs. Recomputed from the database on every run. Serial ascending order is a correctness requirement (a term discovered in chapter N must be visible to chapter N+1); see risks for throughput. Chapters pushed later simply have no row and are picked up by the next run against the same glossary — consistency for later additions falls out of the model.

### D6. Fidelity is deterministic-first, then one audit call, then one repair

Same routing shape as `routeAfterAudit` / `routeAfterFidelityJudge`. Deterministic (free, always run), in a pure `fidelity-scan.ts`:

- `source_script_residue` — characters of the source script (regex chosen by `original_language`: CJK ideographs, kana, hangul) remain in the output, excluding `preserve`-treatment terms.
- `glossary_violation` — an approved or provisional entry's source term occurs in the original but its target does not occur in the translation.
- `number_drift` — the multiset of Arabic digit runs (full-width normalised) differs between original and translation. Missing numbers are the strongest cheap omission signal for power-system prose.
- `paragraph_drift`, `dialogue_drift`, `length_band` — ratios outside configurable bands (`settings.fidelityBands`, per-language defaults), attention-grade signals.

AI audit `translate-audit` (role `audit`, so it is in `CACHEABLE_ROLES` and identical re-audits hit `llm_cache`) compares **aligned segment pairs**, reporting `omission | addition | meaning_shift | tone_shift | terminology | censorship | untranslated` with excerpts; verdict/issues coherence in `postValidate`. Dirty within `maxRepairs` (default 1) → repair pass; still dirty → persist as `attention` (the spec's "review-required").

### D7. Long chapters are segmented and translated in a checkpointed loop

`segment-source.ts` splits the original at paragraph boundaries into segments of at most `settings.segmentTokens` (default 1,800, counted with `countTokens` from `token-budget.ts`, whose o200k encoding handles CJK). Typical web-novel chapters fit one segment; long ones translate segment by segment with the previous segment's translated tail as context. Each segment is a checkpointed step, so a crash mid-chapter resumes at the segment. Segments join with blank lines; the fidelity scan runs on the joined body, the audit on aligned pairs.

### D8. Glossary decisions do not go through `refinement_proposals`

Hard rule 13 protects canon written by chat/audit/premise/arc-plan. The glossary is pipeline working data exactly like `rebrand_glossary`, and its own approve/modify/reject queue _is_ the human gate. Nothing the pipeline writes reaches `chapters` except through finalize (D4).

### D10. `project_kind` is the workflow axis, extended to four values

Today `kind` (`new_novel | source`) already carries workflow semantics on both sides of the wire: the server seeds bible placeholders only for `new_novel` (`project.service.ts:99`), plan import refuses other kinds, rebrand/reforge/recombine refuse non-`source`, and the web derives the sidebar, labels, colours and list filters from it. It has one value too few: curated-ingest novels land as `new_novel` (`curated-ingest.service.ts:63`) and get the whole authoring sidebar, and translation would otherwise need a third implicit signal beside `kind` and `sourceRef`.

| Value         | Meaning                                                       | Created by                                                                  |
| ------------- | ------------------------------------------------------------- | --------------------------------------------------------------------------- |
| `new_novel`   | Original authoring: idea, bible, plan, drafts, review         | New-novel dialog, both existing doors                                       |
| `source`      | Adaptation of an imported English manuscript                  | Import screen, unchanged                                                    |
| `translation` | Original-language novel translated to English, then published | New-novel dialog, new "Translate a novel" door; `originalLanguage` required |
| `curated`     | Finished English manuscript held for publishing               | Curated ingest and reforge promote                                          |

Screens per workflow (the same list feeds the sidebar, the command palette and a route guard):

| Screen                                                            | new_novel | source        | translation | curated                                        |
| ----------------------------------------------------------------- | --------- | ------------- | ----------- | ---------------------------------------------- |
| Overview, Illustrations, Workflow Runs, Publish, Project Settings | yes       | yes           | yes         | yes                                            |
| Story Bible, Volumes & Arcs                                       | yes       | yes, as today | no          | no                                             |
| Canon Facts, Review Queue, Refinement Chat, Proposals             | yes       | yes, as today | no          | no                                             |
| Chapters                                                          | yes       | yes, as today | no          | yes (read, amend, insert into finalized canon) |
| Source Pipeline, Rebrand, Reforge, Transform                      | no        | yes           | no          | no                                             |
| Translation                                                       | no        | no            | yes         | no                                             |
| Import Plan (deprecated)                                          | yes       | no            | no          | no                                             |

Translation hides Chapters deliberately: English edits go through reopen → edit → finalize on the Translation screen, which already republishes on a content change; a second chapter list would invite conflicting edits. The sidebar lifecycle bar follows the workflow too: authoring keeps Bible → Review; translation shows Originals → Terms → Translate → Review → Publish; curated shows none.

Rejected: keeping the binary enum and adding per-screen predicates (workflow stays implicit, the server cannot gate on it); a separate `workflow` column beside `kind` (two overlapping axes that drift).

### D9. One originals door, two authentications

`TranslationService.upsertOriginal(projectId, chapter, { title, content })` is the only writer of the original columns. It is reached from a session-authenticated route (the paste UI) and from an API-key-authenticated route in the curated-ingest module (the external app). The two cannot share a controller: the package `AuthGuard` sorts ahead of `ApiKeyGuard` and rejects key-only callers (the constraint documented on `CuratedIngestController`). Semantics, copied from `CuratedIngestService.pushChapter`:

- Runs under `SELECT … FOR UPDATE` on the project row so two pushes cannot both compute the same next number.
- **Contiguity**: `chapter` must be `≤ max(number) + 1` — append or overwrite, never a gap (`TRN_010`, mirroring `ING_002`). Serial ascending translation depends on this.
- **Idempotent**: same title and content → no-op (204). Different content on an existing chapter → overwrite the original columns and `content_hash`, and set `source_stale` on its translation row if one exists. The English side is never touched by this door.
- Ownership: session route relies on `ProjectOwnershipGuard` like every project route. The key route is also `:projectId`-addressed, so the same app-global `ProjectOwnershipGuard` middleware runs ahead of the handler and answers a foreign or absent project with `PRJ_001` — the same code the session route gets. The handler additionally re-checks ownership itself, answering with the `ING_001` shape the rest of the ingest surface uses, as a defense-in-depth backstop against the guard's path-matching ever changing rather than the caller's actual first line of defence; it records to `ingest_audit_log` with `source_ref = 'project:<id>'` (the column is a non-null varchar(64)) either way.

- **Output schemas**: `ai/schemas/translation.schema.ts` plus enum entries in `ai/schemas/enums.ts`.
- **Context assembly**: `context/sections.ts` `ContextPurpose` + `'translate_seed' | 'translate'`; labels `style_notes`, `term_policy` (add, never rename). `context-assembler.service.ts`: `TRANSLATE_BUDGET = 12_000`, `forTranslateSeed`, `forTranslate(projectId, chapter, { styleNotes, termPolicy, glossarySlice, prevTranslatedTail }, opts)` — stable: `style_notes` + `term_policy`; volatile: `glossary_slice` + `prev_ending` tail.   - `term-matcher.ts` — script-aware matching. `residue-scan.ts` uses `\b` and a 3-character minimum; both are wrong for CJK (no spaces; two-character names like 叶凡 are the norm). Latin terms keep boundaries and the common-word allowlist; CJK/kana/hangul terms use substring matching with a 2-character minimum.
  - `glossary-slice.ts` — ranks entries by occurrence in the **original**, keeps `preserve` and `approved` entries ahead of `suggested` under the cap, renders approved / provisional / not-terms blocks, returns applied ids and revisions.
  - `fidelity-scan.ts` — the D6 checks in the `{ source: 'fidelity', type, detail, excerpt? }` shape.
  - `segment-source.ts` — D7 segmentation.
  - `script-profile.ts` — per-language regexes and default bands shared by the door's validator and the scan.
- **Graph** `ai/graphs/chapter-translation.graph.ts` (+ barrel entry):

  ```
  loadChapter → assembleContext → segment → translateSegment ⟲ (until last segment) → join → fidelityScan → audit
       ↑ repair (flagged segments only, attempt < maxRepairs)                                          │
       └──────────────────────────────────────────────────────────────────────────────────────────────┘
                                                            → persistTranslation → mergeGlossary → finish
  ```

  `loadChapter` reads `chapters.original_*` (throws `TRN_012` shape if absent), the `translations` row (throws if unseeded), the full glossary, and the previous **translated** chapter's tail. `routeAfterFidelity` is an exported pure router. `persistTranslation` upserts with `revision + 1`, status, `applied_terms`, `source_hash`, both stale flags false, `segments`. `mergeGlossary` inserts `discoveredTerms` as `suggested`/`discovered` with `onConflictDoNothing` after dropping rejected source terms. `WorkflowRunService.runChapterTranslation({ projectId, chapter, jobId? })` follows `runChapterRebrand` (`workflow-run.service.ts:315-331`) verbatim.

## 3. Pushing originals from another app

The originals door (D9) is reachable from outside the forge, so an external app that scrapes or otherwise sources original-language chapters can push them straight into a translation project without a human pasting anything. This section is the contract for that pusher.

**Prerequisites.** The project must already exist in the forge with `kind: 'translation'` and an `originalLanguage` — create it through the ordinary project-create endpoint (or the web "Translate a novel" door) before pushing anything; the ingest surface never creates a project. Authenticate with an API key (`x-api-key` header) whose owner holds the `novel-forge:curate` permission (`CURATE_PERMISSION` in `src/constants.ts`) — the same permission the curated-ingest push door requires. A project owned by someone else answers as `PRJ_001` (not found), from the same `ProjectOwnershipGuard` middleware that runs on every `:projectId` route.

**`PUT /api/v1/ingest/projects/[projectId]/originals/[chapter]`** — body `{ "title": string, "content": string }`. `content` is the untranslated chapter prose in the project's `originalLanguage`.

- **201** — chapter created. Only the next chapter after the current highest is accepted; anything else 409s as `TRN_010` ("originals must be contiguous — add chapter N only after chapter N-1 exists"). Push in order; there is no batch endpoint.
- **200** — an existing chapter's title or content differed from what was sent, so it was overwritten. This is unconditional: overwriting the original for a chapter whose translation is already `finalized`, or that has already been published, still succeeds — it is **not** refused with `TRN_004` (that code only guards the _translation_ side: editing/finalizing a finalized chapter, and deleting an original). What the overwrite does instead is flip `source_stale = true` on that chapter's `chapter_translations` row (if one exists) so a reviewer sees the staleness badge and knows the finalized English no longer matches the source. Decide before pushing an amended original over an already-finalized chapter: the English is left untouched until someone re-runs the translation and re-finalizes.
- **204** — the sent title and content matched exactly (after markdown sanitization) what is already stored. Fully idempotent — safe to retry or re-send the same chapter defensively.
- **422** — a field error on `content` when the text does not look like `originalLanguage` (a script-ratio check against the language's expected script; only applied for a non-Latin source language, so a Latin-script project never trips it). The usual cause is accidentally pushing already-translated English instead of the original.

```bash
curl -X PUT "https://[host]/api/v1/ingest/projects/[projectId]/originals/[chapter]" \
  -H "x-api-key: [api-key]" \
  -H "Content-Type: application/json" \
  -d '{"title": "[chapter title in the source language]", "content": "[chapter prose in the source language]"}'
```

**`GET /api/v1/ingest/projects/[projectId]/originals`** — the manifest, for resuming a push run without re-sending prose already landed:

```json
{
  "projectId": "[projectId]",
  "originalLanguage": "zh",
  "chapters": [
    { "chapter": 1, "contentHash": "[sha-256 digest of the landed title+content]", "translationStatus": null },
    { "chapter": 2, "contentHash": "[sha-256 digest]", "translationStatus": "translated" }
  ]
}
```

`translationStatus` is `null` when the chapter has no translation yet, otherwise one of `translated | attention | finalized | failed`. To resume: fetch the manifest, hash your own copy of each chapter's `{title, content}` the same way (`chapterContentHash` from `@shadow-library/sdk/publishing` — the same digest the forge itself stamps), and push only the chapters whose local hash does not match the manifest's `contentHash`, plus every chapter past the manifest's highest number. A chapter absent from the manifest has never been pushed.

```bash
curl "https://[host]/api/v1/ingest/projects/[projectId]/originals" \
  -H "x-api-key: [api-key]"
```

**Risks and open points**

- **CJK matching** is the biggest correctness trap: reusing `residue-scan.ts` as-is would silently match nothing and skip two-character names. TL3 exists to make this a tested seam.
- **Throughput.** Serial ascending is required for glossary consistency, and the per-project lock allows one job at a time; at roughly a minute per chapter a 3,000-chapter novel is about two days of wall clock, resumable across restarts. Windowed parallelism with bounded drift is a possible follow-up, not part of this plan.
- **Cost** is output-token dominated. `limit`, `auditEnabled: false` and the seed pause keep trial runs cheap.
- **Prompt `kind`** for `translate-chapter` needs a look at what the router derives from it before TL4.
- **`sanitizeMarkdown`** (`common/sanitize-content.ts`) should run on pasted/pushed originals like every other landed prose; confirm it is byte-transparent for CJK punctuation and full-width characters in TL2.
- **The external app's push order.** The contiguity rule means the pusher must send chapter 1 before chapter 2; the manifest tells it where it left off. If the other app cannot guarantee order, the alternative is to accept gaps and have the job translate only the contiguous prefix — decide before TL2.
- **A new chapter shape.** Translation projects hold chapter rows with `locked = false` and null `content`, which no pipeline produced before. TL1 audits the frontier and status computations for it, and TL0's refusals keep generation and planning away from those projects.
- **Backfill scope.** Only curated-ingest rows can be re-kinded mechanically; promoted reforge projects stay `new_novel` until an owner switches them, so for a while some publish-only novels keep the authoring sidebar.
- **Renumbering** (interstitial insert, recombine) is keyed by chapter number; the new table joins the same deny-lists, so the guards refuse rather than corrupt.
- **Target language** is fixed to English per the spec; column names are language-neutral so a target-language column can be added without renames.
